  ```markdown
  :::
  ```

1. **Fatal `\@writefile`/`\contentsline` runaway-argument build failure.**
   Reproduced by building into the dirty pre-existing `build/combined/`
   directory left over from earlier sessions: `pdflatex` reads the old,
   complete `.aux` from a prior successful run at `\begin{document}`, and
   that interacts badly with a fresh compile pass, producing
   `Runaway argument? {\contentsl ... File ended while scanning use of
   \@writefile.` and a fatal "no output PDF file produced" at
   `publication-template.tex:31` (the `\begin{document}` line). Deleting

   completely — confirmed by direct reproduction during planning. Root
   cause: **stale build output directory reused across incompatible runs**,
   not a ReportKit defect in the sense of broken LaTeX generation. The
   `publication_build.py`/`reportkit build` combined mode does not clean its
   own output directory before compiling; that is the operator's
   responsibility, and it was not being honored across the prior work
   sessions that left artifacts in `build/`.
2. **`RK_RENDER_FAILED` / `ModuleNotFoundError: No module named 'pymupdf'`.**

   build` without first restoring `build/.venv`: `reportkit build`'s page
   renderer shells out to `<output-root>/.venv/bin/python`, which must have
   `PyMuPDF` installed via
   `bash /home/iancwm/git/report-kit/publication_pipeline/scripts/setup.sh
   build/.venv` (documented in the engine's own
   `publication_pipeline/README.md`, not currently mentioned in this repo's
   README). Not a bug — a missing setup step this repo's own docs never
   mentioned.
3. **Draft footer even on a clean, successful build.** Confirmed by
   inspecting `python_scripts/reportkit/config.py`'s `resolve_identity()`

   used to look up `(config.get("profiles") or {}).get(selected, {})` —
   since `publication.yaml` has no `profiles:` section at all, no
   `--profile` value changes anything about the resolved identity. This is
   config-side, fixable entirely in this repo: add a `profiles: release:`
   section.

### Task 3: Fix the caption-label leakage (unsupported `\label{}` convention)

**Files:**

  caption line ending in `\label{...}` — confirmed present in

  `04-transformation-processing.md`, `05-orchestration.md`,
  `06-quality-reliability.md`, `07-metadata-governance-serving.md`,
  `08-practitioner-topics.md`, `09-learning-path.md` (run the audit command

**Interfaces:**
- Consumes: the release-profile build command from Task 1.
- Produces: nothing later tasks depend on. Independent of Task 2.

**Context:** already root-caused during planning (see Global Constraints'
explanation of why `\label{...}` in caption text doesn't work and what
replaces it). Concretely, a caption today looks like:
```markdown
Table: Lifecycle overview: stages, decisions, and representative tools. \label{tbl:lifecycle-overview}
```
immediately preceded by the table's Markdown source (a `---`-separated
table, or, for listings, a fenced code block). The fix wraps the whole
table-or-code-block-plus-caption in a Pandoc fenced Div carrying the id,
and drops the trailing `\label{...}` text from the caption line:
```markdown
::: {#tbl:lifecycle-overview}
| ... existing table rows unchanged ... |

Table: Lifecycle overview: stages, decisions, and representative tools.
:::
```
(Div fences use `:::`, three colons, at the start of a line, with no
indentation, both opening — carrying `{#id}` — and closing. This was
verified directly against this exact pipeline's pandoc invocation during
planning: `pandoc -f markdown-raw_tex -t latex` renders it as
`\hypertarget{tbl:lifecycle-overview}{}` ahead of the table, with no
literal `\label{...}` text anywhere in the output.)

The same wrapper applies to `Listing:` captions around fenced code blocks.

  form to fix in the manuscript (figures are referenced via
  `[[REPORTKIT-VISUAL:fig:...]]` sentinels resolved against

- [ ] **Step 2: For each hit, wrap the table/listing in a Div with the id, and drop the trailing `\label{...}` text**

  For a table hit, find where the table's Markdown source begins (the
